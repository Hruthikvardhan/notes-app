----------------------------------------------------------------
SECTION 1 — WHY TWO PLATFORMS
----------------------------------------------------------------

Unlike a frontend-only SPA, this project has a real Express/
MongoDB backend that must stay running and hold persistent
connections (DB, JWT). Vercel is built for static sites and
serverless functions, not a long-running Node server with
Mongoose connections, background jobs, and file uploads — so:

  BACKEND  (server/)  →  Render   (Node Web Service, free tier)
  FRONTEND (client/)  →  Vercel   (static SPA hosting, free tier)

The frontend calls the backend's public HTTPS URL over the
network — the two are not on the same domain, so CORS and
cookie settings must be configured correctly (covered below).

SECTION 3 — MONGODB ATLAS SETUP
----------------------------------------------------------------

STEP 3.1 — CREATE OR REUSE A CLUSTER
---------------------------------------
1. Go to https://cloud.mongodb.com
2. Use an existing free (M0) cluster, or create a new one
3. One cluster can safely host multiple projects — just give
   each project its OWN database name so collections don't
   collide (e.g. two projects both having a "users" collection)

STEP 3.2 — CREATE A DEDICATED DATABASE FOR THIS PROJECT
-----------------------------------------------------------
You do NOT need to manually create the database — MongoDB
creates it automatically the first time your app writes data
to it (e.g. on first user registration). Simply choose a
database name and put it in your connection string, e.g.:

  mongodb+srv://<user>:<pass>@<cluster>.mongodb.net/notes-app-mern?retryWrites=true&w=majority

The "notes-app-mern" segment is the database name — change it
to isolate this project's data from any other project sharing
the same cluster.

STEP 3.3 — NETWORK ACCESS
-----------------------------
1. Atlas → Security → Network Access
2. Add IP Address → Allow Access from Anywhere (0.0.0.0/0)
   (fine for a portfolio project; a real production app would
   restrict this to known server IPs)

STEP 3.4 — DATABASE USER
----------------------------
1. Atlas → Security → Database Access
2. Confirm a database user exists with a username/password
   (this is DIFFERENT from your Atlas login — it's what goes
   in the connection string)

SECTION 5 — PREPARE THE FRONTEND FOR A SEPARATE BACKEND HOST
----------------------------------------------------------------

In development, Vite's dev server proxies /api/* requests to
localhost:5000 (see client/vite.config.js). In production there
is no proxy — the frontend and backend live on different
domains — so client/src/utils/api.js must be able to point at
an explicit backend URL:

  const baseURL = import.meta.env.VITE_API_URL
    ? `${import.meta.env.VITE_API_URL}/api`
    : '/api';

  const api = axios.create({ baseURL, withCredentials: true });

This means:
  - Locally, with no VITE_API_URL set, it still uses the Vite
    proxy ('/api') exactly as before
  - In production, Vercel injects VITE_API_URL at build time
    and every request goes straight to the Render backend

Commit and push this change before deploying.

SECTION 7 — DEPLOY THE BACKEND TO RENDER
----------------------------------------------------------------

STEP 7.1 — CREATE A NEW WEB SERVICE
----------------------------------------
1. Go to https://render.com → sign in with GitHub
2. Click "New +" → "Web Service"
3. Select your repo

STEP 7.2 — CONFIGURE THE SERVICE
--------------------------------------
  Name             : notes-app (or any name)
  Language/Runtime : Node
  Root Directory   : server
  Build Command    : npm install
  Start Command    : npm start          ← NOT "npm run dev"
  Instance Type    : Free

  IMPORTANT: use "npm start" (runs `node server.js`), never
  "npm run dev" (runs nodemon, a dev-only file-watcher that is
  a devDependency and shouldn't run on a production server).

STEP 7.3 — ADD ENVIRONMENT VARIABLES
-------------------------------------------
Use Render's "Add from .env" button to paste the whole block
at once, or add them individually:

  PORT=5000
  NODE_ENV=production
  MONGO_URI=<your Atlas connection string with the project's db name>
  JWT_ACCESS_SECRET=<long random string>
  JWT_REFRESH_SECRET=<different long random string>
  JWT_ACCESS_EXPIRY=15m
  JWT_REFRESH_EXPIRY=7d
  CLOUDINARY_CLOUD_NAME=<your cloud name>
  CLOUDINARY_API_KEY=<your api key>
  CLOUDINARY_API_SECRET=<your api secret>
  CLIENT_URL=http://localhost:5173   ← temporary placeholder,
                                         updated in Section 9

  NODE_ENV must be "production" here (not "development") —
  this enables secure cookies and hides stack traces from
  error responses.

STEP 7.4 — DEPLOY
-----------------------
1. Click "Create Web Service" / "Deploy Web Service"
2. Watch the build logs for:
     ==> Build successful
     ==> Running 'npm start'
     Server running on port 5000 [production]
     MongoDB connected: <cluster-host>
     ==> Your service is live 🎉
3. Note the live URL, e.g.:
     https://notes-app-xxxx.onrender.com

STEP 7.5 — VERIFY THE BACKEND
-----------------------------------
Visit <your-render-url>/api/health in a browser.
Expected response:
     {"status":"ok","timestamp":"..."}

NOTE ON FREE TIER: Render's free instances spin down after
~15 minutes of inactivity. The next request after that will
take 30-50 seconds to "wake" the service — this is expected
behavior on the free tier, not a bug.

SECTION 9 — CLOSE THE LOOP: UPDATE CORS ON RENDER
----------------------------------------------------------------

The backend's CORS config only allows requests from the origin
in CLIENT_URL. Right now that's still set to the localhost
placeholder from Section 7.3 — this must be updated or the
live frontend's requests will be blocked by CORS.

1. Go to Render → your service → Environment
2. Edit CLIENT_URL to your real Vercel URL, e.g.:
     CLIENT_URL=https://notes-app-xyz.vercel.app
3. Save — Render automatically redeploys with the new value

SECTION 11 — AUTOMATIC RE-DEPLOYS (FREE ON BOTH PLATFORMS)
----------------------------------------------------------------

Both Render and Vercel watch your GitHub repo. Every push to
main triggers an automatic redeploy on both platforms:

  1. Edit code locally (frontend or backend)
  2. Test locally (npm run dev on both)
  3. git add . && git commit -m "..." && git push
  4. Render rebuilds the backend automatically
  5. Vercel rebuilds the frontend automatically
  6. Both live URLs update within a couple of minutes

Check deploy status:
  - Render: dashboard.render.com → your service → "Events"/"Logs"
  - Vercel: vercel.com/dashboard → your project → "Deployments"

SECTION 12 — TROUBLESHOOTING COMMON ISSUES
----------------------------------------------------------------

ISSUE 1: CORS error in browser console on the live site
  Cause : CLIENT_URL on Render doesn't match the Vercel URL
  Fix   : Update CLIENT_URL on Render to the exact Vercel URL
          (including https://, no trailing slash), redeploy

ISSUE 2: Frontend loads but every API call fails / hangs
  Cause : VITE_API_URL missing or wrong on Vercel, or backend
          is still spinning up from idle (free tier cold start)
  Fix   : Verify VITE_API_URL in Vercel's Environment Variables;
          wait 30-50s and retry if the backend was idle

ISSUE 3: "Route not found" JSON when visiting the backend
          root URL directly
  Cause : This is expected — the backend has no UI, only
          /api/* routes. Visiting / or /login on the Render
          URL will always 404; that's normal
  Fix   : Not a bug — test the frontend at the Vercel URL, and
          the backend only via /api/health or actual API calls

ISSUE 4: Logged out unexpectedly / refresh token doesn't work
          cross-origin
  Cause : Refresh token cookie is httpOnly + secure; needs
          NODE_ENV=production on Render and withCredentials:
          true on the frontend Axios instance (already set)
  Fix   : Confirm NODE_ENV=production on Render; confirm
          CLIENT_URL matches exactly

ISSUE 5: Backend build fails with "Cannot find module"
  Cause : A dependency wasn't installed / package.json out of
          sync
  Fix   : Run npm install locally, commit the updated
          package-lock.json, push again

ISSUE 6: Images don't upload in production
  Cause : Cloudinary env vars missing or incorrect on Render
  Fix   : Double check CLOUDINARY_CLOUD_NAME/API_KEY/API_SECRET
          in Render's Environment tab

ISSUE 7: Accidentally overwrote .env locally
  Cause : Re-running "copy .env.example .env" overwrites any
          edits already made
  Fix   : Re-enter MONGO_URI and JWT secrets; consider keeping
          a backup copy outside the repo while developing

ISSUE 8: .gitignore accidentally excludes .env.example
  Cause : A malformed .gitignore can list .env.example alongside
          .env, stripping out the safe template file that should
          be committed for anyone else setting up the project
  Fix   : .gitignore should only exclude node_modules/, .env,
          dist/, .DS_Store, and *.log — never .env.example

ISSUE 9: MongoDB connection times out on first run locally, then
          works on retry
  Cause : mongodb+srv:// connection strings resolve multiple
          shard hosts via DNS SRV lookup; on some networks the
          very first attempt can be slow enough to hit Mongoose's
          default 10-second buffering timeout, even though the
          connection string and credentials are correct
  Fix   : Simply restart the server (npm run dev again). If it
          fails repeatedly, verify DNS resolution works with
          nslookup -type=SRV _mongodb._tcp.<cluster-address>
          and verify raw TCP connectivity to port 27017 with
          Test-NetConnection (PowerShell) before assuming the
          credentials or Atlas network access rules are wrong

SECTION 13 — FREE TIER LIMITS
----------------------------------------------------------------

RENDER (Free Web Service)
  - Spins down after ~15 min inactivity (cold start ~30-50s)
  - 750 free instance-hours/month
  - Fine for a portfolio/demo project

VERCEL (Hobby plan)
  - Unlimited deployments
  - 100 GB bandwidth/month
  - 6,000 build minutes/month
  - Free HTTPS + global CDN

MONGODB ATLAS (M0 Free Cluster)
  - 512 MB storage
  - Shared vCPU
  - Enough for a demo project's data volume

CLOUDINARY (Free tier)
  - 25 GB storage / 25 GB monthly bandwidth
  - Enough for note images and avatars at demo scale
